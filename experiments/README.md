# Measurement harness for the Telaah 2 evaluation

This directory holds the tooling that produces the evidence for the revised BAB III and BAB IV of the syncguard thesis: the Python package `harness/`, its tests in `tests/`, the lock probe in `lockprobe/`, and the operator runbook in `runbooks/`. Collected data goes to `data/<session>/`, which git ignores. Tables, figures, and `values.json` go to `results/`.

## Setup

```
cd /Users/heed/Projects/syncguard
python3 -m venv experiments/.venv
experiments/.venv/bin/python -m pip install -r experiments/requirements.txt
cd experiments && .venv/bin/python -m pytest
```

Call pytest through `.venv/bin/python`. A bare `python3 -m pytest` is rewritten by the rtk shell hook into a `pytest` binary that is not on PATH.

## Sessions

Every run belongs to a session `S<n>`. S1 to S3 name the archived pre-revision sessions; `start` assigns S4 and up. The forensics document labels the archived process pairs W0 to W5, and the session map keeps those labels.

`start` writes `metadata.json` before anything else happens: session id, purpose, start time in UTC and local time with milliseconds, the host UTC offset, the commit of this checkout and its `git describe --always --dirty` (`harness_describe`), the build identity of `bin/syncguard` read with `go version -m` (Go version, `vcs.revision`, `vcs.time`, `vcs.modified`) and the sha256 of the binary, `syncguard_version` as `git describe --always <vcs.revision>`, the commit and branch of story-localnet, the image IDs of `story-node:localnet` and `story-geth:localnet`, the image IDs of the monitoring stack (`prom/prometheus`, `grafana/grafana`, `grafana/loki`, `grafana/promtail`, all `:latest`, stored under `monitoring_images` and left out of `config_id`; an image docker does not have is null), the sha256 of `genesis-node.json`, the validator set with voting powers, the slashing and evidence parameters, the container clock offset with its uncertainty, and the host hardware line. Copies of `config.yaml` and `config-passive.yaml` are stored as `config.redacted.txt` and `config-passive.redacted.txt`; each starts with the line `# session: <id>` and has the `secret:` value replaced by `<redacted sha256:XXXXXXXXXXXXXXXX>` (the first 16 hex characters of sha256 of the secret). `start` refuses a binary whose `vcs.modified` is true, because its revision would not name what ran. It also refuses a config it cannot redact safely: no secret line, an empty value, a block scalar, a repeated secret key, an escaped quote, or an unquoted value that starts with `#`, `&`, `*`, or `!`.

`config_id` is the first 12 hex characters of sha256 over the build (binary sha256 and `vcs.revision`, story-localnet commit, image IDs, genesis sha256) and both redacted configs; the checkout's `harness_describe` and the monitoring image IDs do not enter it. Iterations with different `config_id` values are never summarized together.

## Clocks

The harness reads two clocks.

1. Host clock: the macOS wall clock of the MacBook Air (Apple M4). syncguard runs on the host and logs host local time (WIB, UTC+7) with milliseconds, for example `time="2026-10-05 09:54:39.620"` (layout `2006-01-02 15:04:05.000`, `internal/constants/logging.go`). Fault-injection instants, monitor samples, and the drill operator's commands are host-clock stamps taken with `time.time_ns()`.
2. Container clock: Docker Desktop runs all containers in one Linux VM, so the containers share the VM kernel clock. CometBFT block header times and precommit timestamps come from this clock.

Offset measurement: at `start` the harness runs `docker exec validator3-node busybox adjtimex` five times. Each output gives the kernel time as `time.tv_sec` and `time.tv_usec`; the harness compares it with the midpoint of the host time read before and after the call. The offset of one sample is container time minus that midpoint. The stored `offset_ms` is the offset of the sample with the smallest round trip, because the midpoint assumption errs by at most half of that round trip; `offset_uncertainty_ms` is that half. All five samples and round trips are kept. The spec named `date +%s%N`, but the BusyBox `date` in the Alpine node images prints whole seconds for that format (it printed `1791172876` on 2026-10-05); `busybox adjtimex` without options only reads the clock and reports microseconds.

Conversion: host time = container time - offset. The analysis applies it to every header and precommit time before computing any metric and copies `offset_uncertainty_ms` into every failover row as `clock_uncertainty_ms`. Resolution: syncguard logs 1 ms; precommit timestamps 1 ns, truncated to 1 ms.

## Metrics

- TTD = t_deteksi - t_gagal.
- TTR = t_aktif_cadangan - t_gagal = deteksi + orkestrasi + mulai node, where deteksi = TTD, orkestrasi = t_alih - t_deteksi, mulai node = t_aktif_cadangan - t_alih. A row is invalid, with `invalid_reason` and empty TTR, orkestrasi, and mulai node, when no signing gap was observed, when no signature follows the gap, or when a phase duration is negative. Summaries skip invalid rows and report each reason with its count.
- Failback, all counted from t_sehat_utama: tunggu grace = t_failback_dipertimbangkan - t_sehat_utama; ke failback selesai = t_failback_selesai - t_sehat_utama; ke tanda tangan primer = t_aktif_utama - t_sehat_utama (TFB). Eksekusi = t_failback_selesai - t_failback_mulai.
- G_fb (s) = t_aktif_utama - t_rilis, the signing gap of the failback (equation 3.7 of the thesis draft). Summaries give the mean and the maximum.
- Missed heights: the heights strictly between the last signature before the gap and the first one after it. `gap_heights` counts all of them; `absent_heights` counts those where 48DC2183 is in neither the signers nor the nil voters; `nil_heights` counts those where it voted nil. Story's x/slashing counts only absent votes as missed (`missed := signed == comet.BlockIDFlagAbsent`, cosmos-sdk piplabs fork, `infractions.go`), so the slashing share and every table column named Tinggi terlewat use `absent_heights`. Every height in between must be present in `heights.jsonl`; otherwise the analysis stops, because a missing commit could hide a signature. The gap starts at the first unsigned height whose header time is at or after the reference instant, so a precommit cast between the kill command and the process's death does not end the outage.
- Slashing share: with `signed_blocks_window` 200 and `min_signed_per_window` 0.05, cosmos-sdk x/slashing jails a validator when missed blocks exceed 200 - round(200 x 0.05) = 190. Each incident reports absent/200 and absent/190.
- Block rate: blocks whose header time falls in a window, times 60 000, divided by the window length in ms. Windows: [t_gagal - 60 s, t_gagal), [t_aktif_cadangan, t_aktif_cadangan + 60 s), and the following 120 s. A window is reported only when `heights.jsonl` holds a block before it, a block after it, and every height in between.
- Availability (soak), equation 3.4: (T - D) / T with T the observation window and D the sum of the signing-gap durations of 48DC2183 inside it. A gap runs from the validator's last signature before an unsigned run to its next signature (at the edges of the stored range, to the header time of the first or last height). D takes the TTR of each failover and the G_fb of each failback, plus every other gap that no measured failover or failback interval explains. `analysis.json` stores D, its parts, and the other gaps under `soak`.
- Availability (soak), equation 3.8, reported beside it as `availability_blocks`: heights signed by 48DC2183 with `block_id_flag` 2, divided by all heights in the contiguous range.

## Signing records

Signatures come from `GET /commit?height=N` on rpc1 (port 26657). `block_id_flag` 2 is a signature for the block and counts as signed; 3 is a nil precommit (the process voted but not for the block) and does not count as signed or as missed; 1 is absent. The harness reads only heights at least 2 below the tip for signatures, because the tip commit can still lack late precommits.

## Statistics

Per metric and configuration: n (iterations with a value) of N (iterations), mean, sample standard deviation with n - 1, minimum, maximum, and the 95% interval mean ± t(0,975; n - 1) x SD / sqrt(n). The t values for df 1 to 30 come from the NIST/SEMATECH e-Handbook of Statistical Methods, section 1.3.6.7.2, column 0.975. With n = 1 there is no SD and no interval; with n above 31 the table has no critical value, so the interval is empty and `ci_reason` says why (no exception is raised). Samples that are not independent, such as the 120 `ps` readings per node of a 10-minute overhead run (a time series of a decaying average), are described with n, mean, sample SD, minimum, and maximum only (`describe` in `harness/stats.py`), with no t-interval. Summaries are per session and `config_id`: no summary pools sessions, so a table covers exactly the rows of its session.

## Safety evidence

- Dual-signer monitor: during every fault-injection run the harness polls `/status` on ports 21657 and 22657 once per second (0.8 s request timeout) and records `validator_info.address` per node, or `unreachable`. When the published port of validator1-node does not answer (a network partition removes it while the process keeps running), the monitor reads the same field inside the container with `docker exec validator1-node wget -qO- http://127.0.0.1:26657/status` (2 s timeout) as a second source; a sample from this source is informative. `dual_signer_seconds` is the number of distinct seconds in which both nodes reported 48DC2183; it must be 0. `indeterminate_seconds` counts seconds in which one node was unreachable and the other reported 48DC2183: the unreachable node could have been signing, so these seconds are neither proven single-holder nor proven dual-holder.
- Monitor coverage: one rule, `coverage(samples, start_ms, end_ms)` in `harness/monitor.py`, decides every "observed" flag of the harness. A sample is informative when it has no sampling error and at least one node answered. A window is observed when an informative sample lies within 5 s of its start and of its end, no two consecutive informative samples are more than 5 s apart, and no sampling error happened within 5 s of it. Indeterminate seconds inside a window are a separate fact: they are reported beside the flag and do not make the window unobserved. The rule is applied per run window (`run_windows` in `harness/analysis.py`): a failover iteration from `iteration_start` to `iteration_end`, a hang or partition run from its fault to its `iteration_end`, a drill from the kill to `restore_end`, a soak from `soak_start` to `soak_end`; a run that aborted ends at its last event. A session is observed when every run window in it is observed; the time between runs needs no samples, and `finish` never compares the samples with its own clock. `safety.json` keeps each window under `monitor.windows`. `observed_problems` lists codes with parameters (`no_samples`, `late_first_sample`, `early_last_sample`, `gap`, `sampling_errors`) and the run they belong to; the Markdown tables and `values.json` show them in Indonesian through `harness/labels.py`, and the CSV keeps the codes. Without an informative sample `dual_signer_seconds` and `indeterminate_seconds` are null. A dual-signer count with `observed` false is printed as not fully observed, never as a clean 0. Tabel 4.7 and `tabel-partisi` use the same rule, so "Monitor mengamati seluruh interval" means the same in both.
- Chain check of unobserved intervals: `unobserved_intervals(samples, start_ms, end_ms)` in `harness/monitor.py` returns, from the same informative samples and the same 5 s reach, every stretch of a run window the coverage rule cannot vouch for: the whole window when no informative sample lies near it, the window start to a first informative sample more than 5 s after it, a last informative sample more than 5 s before the end to the window end, and each pair of consecutive informative samples more than 5 s apart (such a pair can lie up to 5 s outside the window). `coverage` takes its `late_first_sample`, `early_last_sample`, and `gap` lengths from these intervals, so the two cannot disagree. `analyze` adds `monitor_gaps` to `analysis.json`: per run window (scenario and iteration), each interval with its length, the heights whose header time lies in it, and every vote of 48DC2183 whose timestamp lies in it (`votes_inside`, both ends inclusive; `kind` is `commit` for a signature and `nil` for a nil vote, read from `heights.jsonl` shifted onto the host clock). The block is null without `monitor.jsonl` or `heights.jsonl`, and an empty list for a session without run windows. The check reports what the chain recorded while the monitor saw neither node; it does not change `observed`, which stays false for every window with an unobserved interval. Tabel 4.7 shows the intervals per session (Interval tak teramati: `<n> interval, maks <s> detik`, or `tidak ada`) and the count of 48DC2183 votes inside them (Suara 48DC2183 di dalam interval); both read `tidak tersedia` when `analysis.json` has no `monitor_gaps`.
- Forward evidence scan: H is the lowest height of any fault injection in the session. At `finish` the harness reads `block.evidence.evidence` of every height from H to the tip, with no tip margin because block evidence is final at the tip, and reports the range, the count, and the evidence types. Evidence of a double sign at height h can only be committed in a block after h, so a scan of blocks before H, or a backward scan from a halted chain, cannot test the claim (finding IV-10). CometBFT expires evidence only when its age exceeds both `max_age_num_blocks` (100000) and `max_age_duration` (48 h) (`evidence/verify.go`, `IsEvidenceExpired`). The scan records how many blocks and seconds it spans and whether it passed both limits; a shorter scan covers the evidence committed up to its last height only. `finish` refuses a session whose earliest fault event has no height.
- Signing info: `GET http://localhost:1317/slashing/signing_infos/0x<hex of the 33-byte compressed public key>` (for 48DC2183: `0x02f2e8fa5920d145a8ce823ea49cefd5aeeea6df8768cc5909d5a0471bd9f026f5`). The base64 key form returns HTTP 500 `hex string without 0x prefix`. `tombstoned` and `start_height` are omitted from the answer when false or zero.
- Prometheus: the maximum of `cometbft_consensus_byzantine_validators` and `cometbft_consensus_missing_validators` per node instance over the session, queried as `max_over_time(metric[15s])` at the 15 s scrape step, when Prometheus answers on port 9090. When a series returns nothing the result is `{"available": false, "reason": ...}`, because then the check did not run.

## Scenarios

Every runner checks its preconditions first and refuses to start when one fails. No runner repairs the environment, with one logged exception: the partition runner's host-port repair after the reconnect, described in its row. Every docker action is logged in `events.jsonl` with its exact command and exit code.

| Scenario | Preconditions | Action and outputs |
|---|---|---|
| failover | validator1 key file and loaded key are 48DC2183, validator2 holds neither; both syncguard logs past `SyncGuard failover manager started` and not stopped; both processes running; the primary state lock names the active syncguard PID; 48DC2183 signed the newest readable height; the tip rises within 6 s; the last takeover or failback is at least 90 s old (warm-up) | `docker kill validator1-node`; waits for takeover, the backup's first signature (cast after the kill command ended), failback, the release, and the primary's first signature; snapshots before the fault, after takeover, and after failback in the chosen iterations; 100 s stabilization; then the log window and heights are stored. An `iteration_result` event records the outcome before the final heights are read. The series stops at the first outcome other than `complete` and logs `series_aborted`; earlier iterations stay valid |
| hang | as failover | `docker pause validator1-node`; waits up to 60 s for detection and records the measured TTD. The analytic bound of the hang TTD is 35 s: a hung health check takes 2 x `health.timeout` = 10 s, longer than the 5 s interval, and Go's `time.NewTicker` (`internal/manager/failover.go:289`) delivers the pending tick at once, so checks run back to back and TTD lies between `retry_attempts` x 2 x timeout = 30 s and interval + 30 s = 35 s; the 60 s wait only bounds how long the runner looks; then waits up to 2 x `stop_timeout` + 30 s for syncguard to log a terminal outcome (handover or `Aborting failover, staying active`); records whether syncguard's restart of the paused container succeeded or failed, in log order. The hang ends with `docker unpause` only when the container is still paused, syncguard aborted without handing the key over, no other process signed as 48DC2183 since the pause (commits read through the tip), the backup answers `/status` with a non-validator address, and no handover marker appeared in a last poll before the command. Every other case, including any doubt, ends with `docker kill`; a container that is no longer paused needs no action. An abort or Ctrl-C after the pause kills a container left paused. `hang-<n>.json` always carries every key of `RESULT_KEYS` |
| partition | as failover, plus the primary is attached to exactly one docker network at the compose address 10.0.0.21 (read with `docker inspect validator1-node --format '{{json .NetworkSettings.Networks}}'`, never assumed); every failed precondition is listed together | `docker network disconnect <network> validator1-node` isolates a live primary that still holds the validator key (the split-brain question). The published RPC port is expected to disappear with the endpoint, so syncguard's health checks fail, but the runner records what actually happened. The `fault_injected` event carries `fault_kind` `partition`, the network, the exact argv, the exit code, the issue and end times, and the fault height; a failed disconnect is trusted only when `docker inspect` shows the container still attached, and an unreadable inspect aborts the run. One deadline of 180 s from the end of the disconnect command bounds the waits for detection (at most 60 s, `Maximum failures reached`), the backup's takeover (`Successfully took over as active validator`), and the backup's first 48DC2183 signature (flag 2 only, searched from the disconnect command's end). The runner reconnects at the backup's first signature or at that deadline, whichever comes first, with `docker network connect --ip <ip> [--alias <a> ...] <network> validator1-node`, using the address and aliases read before the disconnect; it inspects before (syncguard's restart may already have re-attached the container, which is recorded and needs no connect) and after, and a different address is `reconnect_failed`. Right after a verified reconnect the runner checks the primary's host ports and, when needed, performs an environment repair. Docker publishes a container's host ports only for the networks attached when the container starts: in Sesi S8 syncguard restarted validator1-node while it was disconnected (`restart_before_takeover` true), and after the reconnect `HostConfig.PortBindings` still held `26657/tcp` to 21657 while `NetworkSettings.Ports` was empty, so syncguard on validator1 got connection refused on localhost:21657 and the 300 s failback wait ran out (`no_failback`). One `docker inspect validator1-node --format '{"bindings":{{json .HostConfig.PortBindings}},"published":{{json .NetworkSettings.Ports}}}'` gives both maps (null reads as empty); a binding with a host port is missing when its published list is null, absent, or lacks that port. The first rule that applies sets `port_repair`: ports unreadable, `unknown`; nothing missing, `not_needed`; the container state is not `running`, `not_running` (syncguard may have stopped the node on purpose after a failed restart); the key file address (only the `address` field of `priv_validator_key.json` is read) or the loaded address (`/status` read inside the container with `docker exec validator1-node wget -qO- http://127.0.0.1:26657/status`, up to 3 reads 5 s apart, each with a 15 s command timeout, because in Sesi S8 every 2 s in-container read of the monitor failed for minutes after the disconnected restart while a read without a timeout answered; the monitor keeps its 2 s read) is unreadable or 48DC2183, `refused`, because a restart loads the key file; otherwise `docker restart -t 50 validator1-node` (the compose `stop_grace_period` of validator1-node and syncguard's `stop_timeout`), after which the ports and the endpoint are read again: a non-zero exit is `restart_failed`, a port still missing `still_missing`, unreadable ports `unknown`, otherwise `restarted`, and a primary that is not back at its original address is `reconnect_failed` with the cleanup reconnecting it. The runner never restarts a node that may hold 48DC2183, and it never starts or restarts a container that syncguard stopped. Every run with a verified reconnect logs one `port_check` event (`readable` and `missing_ports`); the restart is logged twice, because `docker restart` can block for the 50 s grace: a `port_republish_issued` event (the exact command, the missing ports, the key file address, and the loaded address) just before the command, and the `port_republish` event (the same fields plus the exit code) after it returns; every state other than `not_needed` is logged as a `port_repair` event with the state, the evidence, and for `refused` the reason; every state other than `not_needed` and `restarted` prints one operator line with the state, the missing ports, and what to check before a manual `docker restart -t 50 validator1-node`. Whatever the state, the run goes on to the failback waits, so a port left unpublished ends as `no_failback` and stops the series. It then waits for `Failback complete - node is now active`, `Successfully released validator duties`, and the primary's first signature, and keeps the dual-signer monitor running 100 s more. A primary that is never detected is still reconnected (`not_detected`). `detection_symptom` is read from validator-1's syncguard log between the disconnect and the detection: from the error text of the `CometBFT health check failed` lines in that window: `rpc_timeout` when any text holds `Client.Timeout exceeded`, `context deadline exceeded`, or `i/o timeout` (each request waited out the timeout, the hang-class bound); otherwise `rpc_refused` when every text holds `connection refused` (the crash-class bound); otherwise `rpc_failure` (any other text such as EOF, connection reset, a non-200 status, or a parse error). Without such lines, `peer_count` when only health lines with peers below `min_peers` (3) and healthy false exist, otherwise `unknown`. ## Commands

Run from `experiments/`:

```
.venv/bin/python -m harness start --purpose "failover n=10, final config"
.venv/bin/python -m harness run failover --session S4 --iterations 10 --snapshot-iterations 1,5,10
.venv/bin/python -m harness run hang --session S5 --iterations 3
.venv/bin/python -m harness run partition --session S5 --iterations 3
.venv/bin/python -m harness run security --session S5
.venv/bin/python -m harness run lock --session S5
.venv/bin/python -m harness run overhead --session S5 --minutes 10
.venv/bin/python -m harness run drill --session S6 --operator "<name>"
.venv/bin/python -m harness run soak --session S7 --hours 24 --kill-offset-hours 6
.venv/bin/python -m harness finish --session S4
.venv/bin/python -m harness scan-campaign --from-session S4
.venv/bin/python -m harness analyze --session S4
.venv/bin/python -m harness report S4 S5 S6 S7
.venv/bin/python -m harness dry-run --out "$(mktemp -d)"
```

`--iterations` (default 1) repeats failover, hang, and partition as a series with one dual-signer monitor across it; the series stops at the first outcome other than `complete`. Any other scenario rejects `--iterations` above 1 with exit code 1. `--snapshot-iterations` applies to failover only and defaults to `1`, so the first iteration takes the three snapshots. `scan-campaign --from-session S4` reads the first fault height of S4, scans block evidence from there to the tip across all later sessions, and writes `data/campaign-scan.json` with the span and its relation to `max_age_num_blocks` and `max_age_duration`; `report` then uses it for the `evidence.*` tokens. `finish` copies the logs before it checks for faults.

Exit codes: 0 done, 1 missing input or bad value, 2 refused by a precondition (every failed precondition is printed). The drill also refuses when stdin is not a terminal. `dry-run` builds the session SFIX from recorded smoke-test fixtures, analyzes it, and reports it; nothing it produces is a measurement, and it never touches docker or the localnet.

## Pemulihan manual bila harness terhenti paksa

The runners reconnect or kill the primary in their abort cleanup, and the CLI turns SIGHUP and SIGTERM into `KeyboardInterrupt` so that cleanup runs. SIGKILL and a power loss cannot be handled, so check `docker ps` and the networks of validator1-node after any forced stop and recover by hand.

- Paused (a hang run stopped before its cleanup): `docker kill validator1-node`, never `docker unpause`. The frozen process may have been handed over already, and resuming it could sign as 48DC2183 beside the backup. Then restore the layout from `runbooks/manual-recovery.md`.
- Disconnected (a partition run stopped between the disconnect and the reconnect): `docker network connect --ip 10.0.0.21 --alias validator1-node <network> validator1-node`. The network name is in the `fault_injected` event of the run (`network`) and in the message the runner printed; `docker network ls` lists it. Check `docker inspect validator1-node --format '{{json .NetworkSettings.Networks}}'` afterwards: the address must be 10.0.0.21. If the container is attached at another address, run `docker network disconnect <network> validator1-node` first and connect again.

## Reports

`report` writes each table twice into `results/`: `.csv` with raw values (epoch ms, dot decimals, full addresses) and `.md` with Indonesian number formatting (decimal comma, thousands dot) and local clock times. Summaries are per session and configuration, and read exactly the rows of the failover table; a soak session's failover appears in the soak table only and is never pooled into Tabel 4.6 or the sensitivity table. Yes and no read Ya and Tidak, outcome and action codes read as Indonesian words in Markdown and stay codes in the CSV, and an aborted series adds a row `Seri dihentikan setelah iterasi k: <hasil>`. Tables: `tabel-4-3-failover` and `tabel-4-3-ringkasan` (Tabel 4.3 with Sumber Bukti, Sesi, the invalid reasons, and Hasil iterasi, so an iteration of an aborted series shows its outcome), `tabel-dekomposisi`, `tabel-laju-blok`, `tabel-4-5-failback` and `tabel-4-5-ringkasan` (Tabel 4.5, with the column G_fb (s) and its mean and maximum), `tabel-4-7-keamanan` (Tabel 4.7, with Monitor mengamati seluruh interval, Interval tak teramati, Suara 48DC2183 di dalam interval, Detik tak tentu, and the monitor's problems), `tabel-uji-negatif` (eight rows, TIDAK TERBUKTI shown), `tabel-uji-lock`, `tabel-snapshot`, `tabel-hang`, `tabel-partisi` (fault height, detected, detection symptom, TTD, takeover, TTR, dual-signer seconds with the indeterminate seconds beside them, the monitor's observed flag and problems, failback complete, and Perbaikan porta host, the `port_repair` state in Indonesian, which reads tidak dicatat for a result written before the field existed, such as Sesi S8), `tabel-overhead` (invalid runs flagged), `tabel-drill` (an unobserved alert printed as tidak teramati), `tabel-soak` (D, equation 3.4 and equation 3.8 availability), `tabel-sensitivitas`, `tabel-peta-sesi`. `tabel-sensitivitas` always has three rows, the measured drill, the 1.800 s assumption, and the 99,1 persen literature value (implied downtime 0,009 x 86.400 = 777,6 s), with the columns Gangguan per insiden baseline (detik), Availability baseline (persen, jendela 24 jam), Availability dengan sistem failover (persen, soak, persamaan 3.4), Selisih (poin persentase), and Penurunan gangguan per insiden (persen). The reduction compares each baseline with the mean TTR of the configuration that has the most valid TTR values; configurations are never pooled.

Figures are PNG at 300 dpi: block height and the 48DC2183 vote per height around the first complete failover of each session (replaces Gambar 4.2), and the signer count per height. `index.md` lists the tables, the figure captions with session and heights, and the tables without data.

## values.json

`report` also writes `values.json`: the values of the {{DATA:name}} tokens that the manuscript draft D/BAB IV lists under "Data tokens", formatted as they appear in the text (decimal comma, thousands dot, seconds to one decimal, percentages to two). The drafts define 122 tokens (draft C and draft D together), the chain check of unobserved intervals adds four, the partition host-port repair adds `partition.port_repair`, and the raw state output of the snapshot points adds six (`raw.*`), 133 tokens in all; `TOKEN_NAMES` in `harness/values.py` lists them. The file has four keys: `values` (name to text), `roles` (which session played the failover series that the draft calls S4, and the hang, partition, drill, soak, security, lock, overhead, and safety parts), `uncomputed` (name to the reason no value was produced), and `extras`. Every token is in exactly one of `values` and `uncomputed`.

`monitoring.versions` lists the image IDs recorded in `monitoring_images` (the images use `:latest`, so the ID is the version) and is uncomputed when a session predates the field or docker lacked an image. `tenderduty.outcome` reads the first line of `data/tenderduty-spike.md` (`kompatibel`, optionally followed by a `sesi: <id>` line, or `tidak kompatibel: <alasan>`) and is uncomputed without that note. `S4.block_time.mean` is the header-time span over the height span of the series heights; `evidence.scan_range` lists the first and last scanned height per session and in total. `partition.tested` is `diuji pada Sesi Sx` (sessions listed when several) whenever a disconnect took effect, whatever the outcome, and `tidak dijalankan` only when every disconnect command failed; each run's outcome is the extra `partition.outcomes`, whose entries name their session (`S8 iterasi 1: ...`) when the runs span more than one session, since iteration numbers restart per session. `partition.method` is built from the recorded argv, such as `pemutusan jaringan Docker kontainer validator1-node (docker network disconnect)`, and `partition.symptom` counts the detection symptoms, such as `kegagalan RPC (3 dari 3 percobaan)`. `partition.session`, `partition.n`, `partition.detected.k`, `partition.ttd.max`, `partition.takeover.k`, `partition.ttr.max`, and `partition.failback.k` count and maximize over the runs whose disconnect took effect; `partition.restart_before_takeover` reads `restart_before_takeover` as `ya pada k dari n percobaan` (with each run's answer when they differ) and is uncomputed for results without that field. `partition.port_repair` counts the `port_repair` states over the runs whose disconnect took effect and that have the field, in the shape of `partition.symptom`, such as `restart kontainer setelah penyambungan kembali (1 dari 1 percobaan)`, and is uncomputed when no such run has the field (results written before the host-port check, such as S8). All of them are explained when no session has a `partition-<n>.json`. When `data/campaign-scan.json` exists, `evidence.count`, `evidence.final_range`, `evidence.heights`, and `evidence.scan_range` describe that one scan instead of the per-session scans. `monitor.unobserved.count` (unobserved intervals), `monitor.unobserved.max_s` (the longest, seconds to one decimal), `monitor.unobserved.votes` (48DC2183 votes inside them), and `monitor.unobserved.heights` (distinct heights inside them) total the `monitor_gaps` blocks of the sessions that have a `safety.json`; a vote or height inside two overlapping intervals counts once, and all four are uncomputed when no such session has the block. A partition's own detection is not counted as an unintended failover (the 60 s wait and 35 s bound of a hang apply). Other tokens are explained when their input is missing, for example `S4.ttr.sd` with one iteration, or the drill tokens when the drill ended without a recovery time. The success-plus-safety and failback criteria count an iteration as safe only when the dual-signer monitor observed its run window by the coverage rule of the safety section; otherwise its safety reads `tidak teramati` and it is not a success. An unintended detection is a `Maximum failures reached` line that is not the iteration's own detection (the first after its fault; for a hang the first within the 60 s wait) and not within the class bound after a fault command (command time plus 15 s for a crash, 35 s for a hang); criterion 5 looks for them over the whole iteration, up to the next iteration's start. `hang.n` counts only pauses that took effect. The file's `extras` key holds values the draft does not define as tokens: `S4.series_aborted`, `S4.series_aborted.reason`, `hang.not_injected`, and `partition.outcomes`. Tokens that depend on log excerpts need the copied logs in `logs/`, and the success-plus-safety and failback criteria need `safety.json` and `monitor.jsonl` of the series session.
